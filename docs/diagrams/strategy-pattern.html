Strategy pattern — resolution & catalog

Every FX trading behavior is an interchangeable strategy implementation, picked at runtime by (ClientId, InstrumentClass) instead of hardcoded per desk — decomposed by capability rather than one wide interface, after building it surfaced a real ISP violation (not every strategy quotes, not every strategy executes). 2 of 10 catalog strategies are actually built; the rest are designed only.

Supporting data — a SQL row, not code (no database exists yet)

StrategyAssignment ClientId · InstrumentClass · StrategyId · Version · EffectiveFrom · Mode (Shadow / Canary / Live)

Promoting a new strategy version is a StrategyAssignment row update, not a deploy — the same binary already runs all three modes. Shadow logs decisions without acting on them; Canary acts, but only for the client/instrument slice named in the row; Live is the default for everyone else. This promotion mechanism, and backtesting via a generic replay harness, are both design intent — neither is built yet.

See the design doc for the reasoning. Part of BEX.
